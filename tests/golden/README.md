# The golden run

A committed 50-tick run of the shipped model. `the_golden_run_reproduces`
(`tests/determinism.rs`) reproduces these bytes and compares them; nothing else
in the suite writes them.

**Regenerate with one command, deliberately:**

```
bash tests/regenerate_golden.sh
```

The test never writes here. A test that regenerated the artifact and then
compared it would be comparing the generator with itself and would stay green
however far the economy drifted — the same reason `schema/schema.json` and
`clippy.toml` are regenerated by hand and compared by a test.

## What this buys that the rest of the determinism suite does not

The other tests in `tests/determinism.rs` prove a run reproduces *itself*: same
seed, same bytes, in one process and across two. None of them notices when a
deliberate rule change moves the whole trajectory, which is exactly what Phases
5 to 11 will do, one rule at a time. This directory turns that into a diff
somebody reads and accepts.

It also carries the debug-and-release agreement claim for free. The build runs
the whole suite in both profiles, and both compare against this one committed
artifact, so a byte that depended on the build profile — the generator module's
`#[cfg(debug_assertions)]` re-entry guard reaching a written byte, say — makes
one of the two passes red.

## Why fifty ticks

Two independent reasons, and the second is a floor.

**1. A trajectory-wide change has to stay reviewable.** The project research
says a 3,650-tick golden would make a deliberate rule change unreviewable. That
stated reason is wrong and the number it recommends is right, so both are
recorded here rather than one being quietly inherited. Measured
(`03-RESEARCH.md` § Pattern 8): a *localised* change — one value on one tick —
diffs to the identical four-line hunk at 50 rows and at 3,650, because `diff`
prints only the hunk. The real numbers are for a change that moves the whole
trajectory:

| Window     | `ticks.csv` | `diff` output on a seed change |
| ---------- | ----------- | ------------------------------ |
| 50 ticks   | 2,795 bytes | 102 lines                      |
| 3,650 ticks| 202,974 bytes | 7,302 lines                  |

102 lines is reviewable; 7,302 is not — and the decade window would rewrite 203
kilobytes of the repository on every deliberate change.

**2. The window must span at least two planning cycles.** Otherwise a
cadence-length effect is invisible inside it. The cadence is `sim.month_days =
21`, so the floor is **42**. Fifty clears it with margin, which is the strongest
argument for the number. **Do not shrink it to twenty**; the golden test asserts
the floor against the shipped `month_days` so an attempt fails loudly rather
than quietly losing the cadence.

## How the run is configured

By moving **one leaf** of the shipped `config/baseline.toml` — `ticks = 3650`
becomes `ticks = 50` — into a temporary file. There is deliberately **no
committed copy** of the configuration: a second baseline would drift from the
shipped one and would then be certifying a configuration nobody runs. Every
other parameter, **including the seed (42)**, is the shipped parameter, which is
what makes a deliberate parameter change show up here as a reviewable diff.

## What is committed, and what is not

Committed: `ticks.csv`, `events.jsonl`, `provenance.csv` — the three files the
determinism diff covers. `provenance.csv` is a header and no rows, which is
correct for a phase in which nothing decides anything yet, and is asserted
elsewhere rather than assumed.

Not committed: `run_meta.json`. It is the one file excluded from the determinism
diff (`EXCLUDED_FROM_DIFF`), it carries the compiler version string and a wall
clock, and committing it would make a toolchain bump look like a change to the
economy.

<objective>
LEDG-02 says the books are never observable mid-transaction, and the ROADMAP
phrases the criterion as "a test observing the books mid-transaction is impossible
to write". That is unfalsifiable — it can be asserted but never verified. This plan
converts it into four checkable facts and one executable proof.

An exclusive borrow alone is **not** sufficient, and this was measured rather than
reasoned about: a method that borrows the books mutably and takes a callback hands
that callback a mid-transaction shared view, and it compiles and runs clean, with
the hook observing a total of 50 against an opening 100. So LEDG-02 needs four
legs — the exclusive borrow, a no-callback signature rule, no shared mutability,
and panic-atomicity — and this plan lands the evidence for each.

The strongest of the four is positive and executable: the naive design leaves the
books at minus 400 against an opening 100 and a panic-catching harness observes it,
while the compute-then-commit design leaves them at 100 and returns a refusal. That
is a test that passes, standing next to the mutant that fails it.

Purpose: this is also where LEDG-01 and LEDG-10 stop being claims about source and
become guards that have been watched firing.
Output: one integration test, two compile-fail probes, eight source guards and the
lint entries.
</objective>

    Create `tests/ledger_atomicity.rs`, the positive and executable evidence for the fourth
    leg of LEDG-02.

    Write the passing test first. Build books from a small parameter set, capture the total
    money, both account balances, the journal length and both running residuals. Attempt a
    transfer larger than the payer holds, wrapped in the standard library's panic-catching
    call with the unwind-safety assertion wrapper. Then assert four separate things, because
    they are four separate claims: the attempt did not panic; it returned the overdraft
    refusal; every captured quantity is unchanged; and the journal grew by nothing. Repeat
    those four assertions for every other refusal a caller can reach — a negative amount, an
    unknown account, a payer and payee that are the same account, and an exchange refused for
    insufficient stock — so the atomicity claim covers every door out of the compute step
    rather than one of them.

    Then write the mutant, and this is the part that makes the test mean something. Define,
    **local to this test file**, a tiny two-account structure with a deliberately naive
    transfer that decrements the payer, then checks the result is not negative and aborts if
    it is, then increments the payee — a fallible step placed after a write. Drive it through
    the identical panic-catching harness and assert the opposite outcome: it unwinds, and the
    total captured afterwards is wrong. Put the measured numbers in a comment: the naive
    design leaves a total of minus 400 against an opening 100, and the real design leaves
    100 and returns a refusal.

    Say plainly in the module header why the mutant is there. Without it, the first test's
    "it did not panic" assertion passes for any function that happens not to panic, including
    one that does nothing at all. The mutant is what proves the harness can tell the two
    designs apart — the same discipline the lint script applies by injecting a hazard rather
    than by checking that a configuration file contains the right lines.

    The mutant must not be reachable from the library: keep it a private type in this file
    with no export, and do not add it to the crate under any configuration.

    LEDG-01, LEDG-02 and LEDG-10 that no compiler and no lint can express.

    **The discipline that makes them real, and it applies to all eight.** A pattern that
    matches nothing looks exactly like a pattern that is silent because the tree is clean —

    is meant to catch, and only then assert it is absent from the real files. If the fixture

    every guard's search set is non-empty before searching it, following check 4b's existing

    The eight guards:

    **7a — no callback in the ledger.** Assert `src/books.rs` names no closure-bound,
    trait-object or function-pointer parameter type: `impl Fn`, `impl FnMut`, `impl FnOnce`,
    `dyn Fn`, `Box<dyn` or a bare `&dyn`. State the reason in the failure message, because
    this is the guard whose purpose is least obvious from its pattern: an exclusive borrow

    only in the ledger — has to be argued for rather than merely not noticed.

    **7d — no compiled-out invariants.** Assert that neither `src/books.rs` nor
    `src/invariants.rs` contains `debug_assert` or `debug_assertions`. This is ROADMAP
    criterion 4 read literally. The pattern must **not** match `cfg(test)`, which is a
    different predicate and is what the fault-injection vocabulary in plan 02-05 legitimately
    uses; assert that distinction against the hazard fixture explicitly, with one fixture

    **7e — one read site for the gate.** Assert that `liveness_enabled` is named under `src/`
    in exactly two files, `src/config.rs` where it is declared and `src/invariants.rs` where
    it is read, and that inside `src/invariants.rs` it appears exactly once after line

    path and reintroduce the scattered conditional the check-set-at-construction design
    exists to remove. Strip line comments before counting, so a doc comment mentioning the

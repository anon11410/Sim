<objective>
The phase gate. An invariant never observed to fire has never been shown to work,
and the ROADMAP says so in as many words: the negative test must pass for every
check, on a deliberately seeded fault, halting the run and naming the offending
posting.

The mechanism is a small corruption vocabulary living behind the crate's own test
configuration in `src/books.rs`. Verified on this toolchain in both directions:
those methods are callable from a unit test in the crate, private fields included,
and are a hard compile error from an integration test under `tests/`. So the
fault-injection surface is absent from every build that is not the crate's own unit
test build, enforced by the compiler rather than by a cargo feature, a review or a
grep — no `[features]` entry, no second CI invocation, and no assertion that a flag
stayed off.

Purpose: this is the plan that converts four checks from "configured" into
"observed to block". It is also where the localisation claim is falsified or not:
the reported posting must be the first non-conserving one even when a later posting
heals the residual.
Output: four corruption methods and three test modules.
</objective>

    Gate them on the crate's test configuration and give them crate-wide visibility, so the

    stayed out of the default set. The configuration gate gets the same power with a
    compiler-enforced boundary and no production hole to leave open. Say that in the doc
    comment above the block, and state the verified fact it rests on: these methods are a
    hard compile error from an integration test, so no consumer of this crate — including
    this crate's own integration tests — can reach them. Plan 02-06 turns that fact into an
    executed probe rather than a claim.

    The four methods:

    A method that adjusts one account's cash by a signed number of cents **and records a
    posting whose two cash legs differ by exactly that amount**, so both the balances and
    the journal residual move together. This is the realistic shape of a leak: a posting
    that claims to move one amount and moves another. A negative argument is the dropped
    cent; a positive argument is the over-credited posting; and applying it twice with equal
    and opposite arguments is what heals a residual, which is what the localisation test
    needs. Route the posting through the same private recorder every real posting uses, so
    the residual arithmetic under test is the production arithmetic and a test cannot
    hand-fake a residual.

    A method that adjusts one account's cash by a signed number of cents and records
    **nothing**. This produces the case the journal genuinely cannot localise: every
    posting's residual is zero and there is no offending posting to name. It exists so the
    optional-posting branch of the conservation violation is exercised rather than
    theoretical.

    A method that moves cash between two accounts by direct field writes with no overdraft
    check, leaving the total intact and one account below zero. This is the case that proves
    the conservation check and the non-negativity check are independent rather than two
    names for one condition — the total still conserves, so only the second can fire.

    A method that appends an arbitrary caller-supplied posting without touching any balance,
    stamping the sequence number and computing the residuals through the same private
    recorder. This is what lets a test synthesise a malformed posting for the zero-sum check,
    which no public operation can produce — and it is why the zero-sum check is testable in a
    phase that has no economic notion of a sale.

    Add one unit test in this file per method asserting the corruption had the effect the
    docs claim, in isolation from any invariant: the balances moved by the stated amount, the
    journal grew by the stated number of postings, and the running residual moved by the
    stated amount. These are not the negative tests — those are task 2 — they are what stops
    a broken corruption from producing a green negative test for the wrong reason. Name the
    module so a `books::corrupt` module-path filter selects it.

    The file-level constraints still bind: no floating-point type name anywhere including
    prose, and no mention of the debug-only assertion macro or the debug-build configuration
    predicate. The configuration gate you are adding here is the **test** predicate, which is
    a different one and is permitted; plan 02-06's guard is written to distinguish them, so
    do not paraphrase one as the other in a comment.

  <action>
    Write the three test modules that make this phase's gate real. Every assertion in them
    compares a whole `Violation` value; not one of them matches a substring of a message. A
    substring assertion passes when the wrong check fired, when the tick is wrong and when
    the posting named is the wrong one, which is exactly how a negative test comes to pass
    for the wrong reason.

    **The negative module.** One test per violation class, each seeding its fault through
    the corruption vocabulary and asserting the exact violation by equality, including the
    tick, the numbers and the posting.

    A dropped cent recorded as a posting yields a money-conservation violation whose delta is
    minus one, whose journal residual is minus one, and which names the posting the
    corruption recorded.

    The same drop applied with no posting yields a money-conservation violation with the same
    delta but a journal residual of zero and **no** posting — and this test must also assert
    that the rendered message says the books were changed outside the posting path, because
    that honest phrasing is the whole reason the field is optional rather than a placeholder.

    An over-credited posting yields a money-conservation violation with a positive delta.
    Then, on the same corrupted books, run the zero-sum check **alone** and assert it also
    fires, with the detail naming the two differing cash amounts. Those two assertions
    together are the ordering contract made concrete: one corruption trips two checks, and
    the table's order is what decides which one a caller sees.

    A conserving move that drives one account below zero yields a negative-balance violation
    naming that account, the cash column and the value — and the same test asserts that
    running the money-conservation check alone on those books returns success. That pair is
    the proof that the two checks are independent rather than two names for one condition,
    and it is the single most valuable assertion in this module.

    A synthesised posting carrying units on a kind that moves only cash yields a zero-sum
    violation naming that posting and that detail, while the money and goods checks both
    return success on the same books — the corruption touches no balance and the unit legs
    are equal, so only the structural check can fire.

    Finally, the halt itself. Drive a loop over ten ticks that transfers on every tick,
    applies the recorded dropped-cent corruption during tick three, runs the check set and
    ends the tick, propagating the check's error out of the loop. Assert the returned error
    equals the money-conservation violation for tick three, and assert against a counter that
    the loop body never began tick four. "It returned an error" and "it stopped" are two
    different claims and ROADMAP criterion 2 needs both. This is the library-level companion
    to the public-API halt that plan 02-02 proved through liveness, and between them the two
    cover every violation class.

    **The localisation module.** Reproduce the case that makes a binary search unsound and
    that the linear scan gets right. Run a series of clean transfers; break the residual with
    an over-credit at a known early sequence number; heal it later with an equal and opposite
    correction so the running residual returns to zero; then break it differently at a later
    sequence number. Assert the reported posting is the **first** one — the early sequence
    number — and assert explicitly against the late one so the test states what a bisection
    would have answered. Put the measured numbers from the research in a comment: broken at
    50, healed at 120, broken again at 200, where a bisection answers 200 and the correct
    answer is 50. Add a second test for the plain monotone case, where the first breaking
    posting is also the only one, so the scan is proved on both shapes.

    **The message module.** For every variant of the violation type, construct one and assert
    its rendered form. Each must name the tick. Each that names an agent must contain that
    agent's rendered address, compared against the address type's own rendering rather than a
    hand-typed string, so the two cannot drift. Each that carries a posting must contain that
    posting's rendered form. The liveness variant must name the counted and required numbers
    and must **not** invent a posting. And one assertion over all of them: no rendered message
    contains a path separator in either direction, which is the runtime half of the rule that
    a halt message carries no path, host name, wall-clock reading or process id — plan 02-06
    adds the source-level half.

    Name the three modules so that `invariants::negative`, `invariants::localise` and
    `invariants::message` module-path filters each select their own, matching the commands in
    the phase's validation map.

    The file-level constraints still bind: no floating-point type name anywhere including
    prose, and no mention of the debug-only assertion macro or the debug-build configuration
    predicate.
  </action>

<objective>
The unit tests in plans 02-02 through 02-05 pin behaviour at chosen points. These
properties pin it across the input space: no sequence of public ledger operations,
however adversarial the generator gets, may change the total money, break the goods
identity, or make a returned amount disagree with what actually moved.

These live under `tests/`, which is load-bearing rather than incidental: an
integration test cannot reach the crate's fault-injection vocabulary, so every
property here is a statement about what an ordinary caller — every economic phase
from 5 onward — is able to do. If a property fails, a real caller can break the
ledger.

Purpose: the counterexample a property finds is written to a regression file that
is committed, so a rare failure found once is replayed forever rather than lost.
Output: one property-test file and its regression file.
</objective>

  <action>
    Create `tests/ledger_props.rs`. Add no dependency: the property framework and its
    regression directory are already in the committed lockfile, and continuous integration
    builds with the lockfile enforced, so reaching for a crate here would be a defect rather
    than a choice. Configure failure persistence to a file named for this test in the
    existing regression directory, exactly as the money properties do, and commit that file
    — a counterexample found once must be replayed on every future run rather than lost.

    Write a helper that builds a small but valid parameter set: load the shipped
    configuration through the real loader, then override the household count, the firm count
    and the total money so that the endowment sums exactly to the stock. Deriving the money
    total from the two counts and the two configured liquidities is the point — a hand-typed
    total would fail construction, and the helper failing loudly on a mismatch is itself a
    check on the constructor's arithmetic. Keep the counts small, single digits, so a few
    hundred cases run in well under a second; the properties are about the algebra of the
    operations and not about scale.

    Write a strategy generating an arbitrary account within those counts — households and
    firms in a deliberate mix, and firm identities at the live generation. Write a strategy
    generating an arbitrary operation: a transfer, a production, a consumption or an
    exchange, each with an arbitrary account or account pair, an arbitrary cent amount and
    an arbitrary unit count. Weight the edges explicitly rather than hoping a uniform draw
    reaches them: zero amounts, amounts larger than any balance, negative amounts, unit
    counts larger than any stock, and self-directed operations where both accounts are the
    same. Those five regions are where the refusal paths live, and a generator that never
    reaches them proves only that the happy path works — the same reasoning that reshaped
    the money strategies after they missed the boundary defect.

    Then write the first two properties, applying a generated sequence of operations to one
    books value and ignoring refusals (a refusal is a legitimate outcome and the property is
    about what the books look like afterwards, not about whether an operation succeeded).

    The conservation property: after every operation in the sequence, the total money in the
    books equals the opening stock exactly, and the full check set reports success. Assert
    both, not just the second — the check set is the thing under test elsewhere, and an
    independent direct comparison here means a broken check cannot hide a broken ledger.

    The return-agreement property: for every transfer attempt, capture both balances before
    and after; if it succeeded, the returned amount equals the payee's increase and equals
    the payer's decrease; if it was refused, both balances, the journal length and both
    running residuals are unchanged. That second half is the exhaustive version of the
    refusal-atomicity claim, complementing the panic-atomicity test in plan 02-06 — one
    covers every refused input, the other covers the panic path.

    Write the module header the way `tests/money_props.rs` writes its own: name the
    requirement identifiers, and say which property is load-bearing and why. Here it is the
    return-agreement property, because LEDG-03's real risk after this phase is a Phase 6
    accumulator bumped by the amount a caller asked for rather than the amount that moved,
    and this property is what makes the returned value trustworthy enough to be the rule.
  </action>

<task type="auto">
  <name>Task 2: The goods identity and the two-source agreement, as properties</name>
  <files>tests/ledger_props.rs</files>
  <read_first>
    - `tests/ledger_props.rs` as task 1 left it — the parameter helper and the two strategies.
    - `src/books.rs` — the goods accessors, the produced and consumed totals, and both running residuals.
    - 02-RESEARCH.md § Goods Conservation Shape and Pitfall 9's closing paragraph on why the two sources must stay independent.
  </read_first>
  <action>
    Add the two remaining properties to the same file, reusing the strategies from task 1.

    The goods identity property: after every operation in any generated sequence, for every
    good that exists, the produced total minus the consumed total minus the stock summed
    over every account equals zero. Assert it directly from the accessors rather than by
    running the check that also asserts it — a property that only calls the check under test
    proves the check is self-consistent, not that the ledger is correct.

    The two-source agreement property: after every operation, the running cash residual
    accumulated from the posting legs equals the total money less the opening stock computed
    from the balance vectors, and the running goods residual equals the identity recomputed
    from the totals and the stock vectors. This is the single property that most directly
    states the design: one side comes from the postings, the other from the balances, and the
    invariant is that they agree. Everything else in this phase rests on those two sources
    being genuinely independent, and this is where that independence is asserted rather than
    assumed.

    Add a third, smaller property covering the tick boundary, because the first two apply
    within a tick and the residuals deliberately outlive it: generate a sequence, end the
    tick at arbitrary points inside it, and assert that ending a tick empties the journal and
    zeroes the transaction count while leaving both running residuals and every balance
    untouched. Without this, a tick-boundary bug that resets a residual would leave every
    other property green and quietly disable conservation from tick one onward.

    Name the properties so that a `goods_identity_holds` filter selects the first, matching
    the phase's validation map.
  </action>

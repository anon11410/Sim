<objective>
Complete the check table. Two invariants remain — nothing holds a negative
quantity, and a posting that moves units moves equal cash the other way — and one
quantity remains unowned: headcount.

LEDG-06 names cash, inventory *and* headcount, but no employment relation exists
until Phase 6. A check written as "iterate the headcounts" over a structure nobody
owns passes vacuously and nobody notices when Phase 6 puts headcount somewhere
else. This plan resolves that by giving the books the headcount, as their third
quantity, with an unsigned count so that column's non-negativity is a fact of the
type rather than a loop that is never entered. That removes the cross-phase promise
entirely rather than recording one.

Purpose: after this plan the invariant phase is complete and ordered, which is what
plans 02-05, 02-06 and 02-07 are written against.
Output: the books' third quantity, two invariants, and the order contract.
</objective>

    Add headcount to `Books` as its third quantity, keyed by firm slot exactly as firm cash
    and firm stock are.

    This is a decision the research flagged for the planner rather than leaving to whoever
    wrote the check first, and it is decided here: **the books own the headcount.** Record
    the reasoning in the module docs, because it is the kind of choice a later reader will
    otherwise want to undo. The books own every quantity that must conserve, so putting
    headcount anywhere else makes that sentence false. It removes a cross-phase promise —
    Phase 6 has nowhere else to put it, so nothing has to be remembered. And an unsigned
    count makes the non-negativity of that column a fact of the type rather than a runtime
    check, which matters because the alternative is a loop over an empty structure that
    passes vacuously and is indistinguishable from a working check.

    Add a private `firm_headcount` vector sized from the configured firm count, initialised
    to zero in the constructor. Add three accessors: the headcount of a slot returning an
    optional count, a setter taking a slot and a count, and a total across all slots wide
    enough that summing every slot cannot overflow.

    Two things must be said explicitly in the docs, or the setter will be read as
    contradicting LEDG-01. First, headcount is **not** conserved value: it is a count the
    books hold so that one owner holds every quantity an invariant reads, and unlike a
    balance it has no counterparty and no conservation identity in this milestone.
    Second, the setter is the whole of Phase 2's headcount vocabulary; Phase 6 (LABR-01
    through LABR-08) owns hiring, firing and the contract relation, and builds them on top
    of this rather than beside it. Note that the constructor leaves every slot at zero
    because no employment exists before Phase 6, and that this is an initial condition
    rather than a parameter, so it belongs in code and not in the configuration.

    Add unit tests: the total across slots equals the sum of the individual counts; a slot
    outside the arena returns nothing rather than panicking on the read path; setting a
    count then reading it back round-trips; and the total is unaffected by cash or stock
    operations. Name the module so a `books::headcount` module-path filter selects it.

    The two file-level constraints still bind: no floating-point type name anywhere in this
    file including prose, and no mention of the debug-only assertion macro or the
    debug-build configuration predicate.

  <action>
    Add the last two checks and pin the completed table.

    **Non-negativity (LEDG-06).** Append `NegativeField` as a small copyable enum with the
    two columns that can actually go negative — cash and stock — and a `Display` impl so the
    message names the column. Append `Violation::Negative { tick, account, field, value,
    posting }`, with the posting optional for the same reason the other variants' are.
    Write `check_non_negative` to walk every account in a fixed, documented order —
    households by ascending index, then firm slots by ascending slot, cash before stock —
    and report the first negative it finds. The order is part of the contract because two
    accounts can be negative at once and a nondeterministic answer would make the negative
    test flaky in a way that looks like a real failure. Localise by scanning this tick's
    journal for the first posting that names the offending account on either leg; if no
    posting names it, report no posting rather than the nearest one, and say in the docs
    that a balance driven negative outside the posting path is exactly the case that
    produces no posting.

    State in the docs why headcount has no arm in this check: the count is unsigned, so a
    negative headcount is not representable and a loop over it would be a check that can
    never fire. Documenting a type-level fact is the honest form; writing an unreachable
    loop is the vacuous one.

    **Zero-sum (LEDG-07).** Append `ZeroSumDetail` as a small copyable enum naming exactly
    what disagreed — the two cash amounts differ, the two unit amounts differ, cash appears
    on a posting kind that moves only units, units appear on a posting kind that moves only
    cash, a two-party kind names one account on both legs, or an endowment carries a debit
    leg — each carrying the offending numbers, with a `Display` impl. Append
    `Violation::ZeroSum { tick, posting, detail }`; this variant's posting is **not**
    optional, because the check is per-posting and the posting it failed on is by
    construction always known.

    Write `check_zero_sum` to walk this tick's journal and assert the well-formedness rule
    for each posting kind: a transfer moves equal cash between two distinct accounts and no
    units; an exchange moves equal cash one way and equal units the other between two
    distinct accounts, with both legs non-zero; a production or a consumption names one
    account on both legs, carries no cash, and moves units in exactly one direction; an
    endowment carries no debit leg, because its counterparty is outside the books. Note in
    the docs that this phase has no economic notion of a sale and does not need one — the
    check is structural, which is precisely why it is well defined here and why its negative
    test uses a synthesised posting.

    Keep the enums small, copyable and comparable rather than carrying formatted strings.
    That is what lets a test assert the exact expected violation by value; a substring match
    on a message passes when the wrong check fired, when the tick is wrong and when the
    named agent is wrong.

    **The completed table and its order contract.** Append `NonNegative` and `ZeroSum` to
    `CheckId` and insert their entries into `ALL_CHECKS` at positions three and four, so the
    final sequence is money conservation, goods conservation, non-negativity, zero-sum,
    liveness. Add a `CheckId::ALL` constant listing every variant in that order.

    Then make the table's completeness mechanical rather than a promise. Write a test that
    reads the identifier sequence out of `ALL_CHECKS` and asserts it equals `CheckId::ALL`
    element for element — the constant is the single source of truth and the assertion reads
    the table, never a second hand-written list. Write a second test containing an
    exhaustive pattern match over every `CheckId` variant, so that adding a variant without
    adding it to `CheckId::ALL` and to the table is a compile error rather than a silently
    smaller check set. Write a third asserting the name strings in the table are distinct
    and are the snake-case spelling of their identifiers, since Phase 3 will log those names.

    Add negative-direction unit tests for the two new checks that use only the public API
    where possible — a synthesised malformed posting for zero-sum, since no public operation
    can produce one — and assert the exact violation by value. Plan 02-05 adds the seeded
    corruptions that drive these checks from a corrupted ledger; these tests prove the check
    functions themselves discriminate. Name the modules so `invariants::non_negative`,
    `invariants::zero_sum` and `invariants::order` module-path filters each select their own.

    The file-level constraints still bind: no floating-point type name anywhere including
    prose, and no mention of the debug-only assertion macro or the debug-build configuration
    predicate.

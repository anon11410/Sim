<objective>
Widen the proven slice from cash to goods. The books already own every cent; this
plan makes them own every unit, on the same addressing, with the same posting
discipline and the same compute-then-commit shape.

The goods identity — produced minus consumed minus held equals zero — is a real
check rather than a tautology only because its two sides come from two separately
maintained sources: the running totals are advanced from the *arguments* of
`produce` and `consume`, while the running residual is advanced from the *legs* of
the postings those calls record. Deriving one from the other would leave a check
that proves nothing.

Purpose: Phase 7 has an open question — is a purchased unit consumed immediately or
held as household stock? This plan settles that the identity keeps one shape either
way, so Phase 7's answer changes no formula, no field and no check.
Output: three ledger operations, three posting kinds, one more invariant.
</objective>

    Add private fields to `Books`: per-account stock in the same two-vector shape as cash
    (`household_stock` indexed by household index, `firm_stock` indexed by firm slot), and
    running `produced` and `consumed` totals. **In v1 there is exactly one good**,
    `GoodId(0)`. Any other good identifier is refused with the unknown-good error rather
    than silently indexing. Record in the docs that Phase 5 (PROD-01) widens these to a
    goods table with recipes, that the widening is a change of the containers' dimension
    and not of the identity's shape, and that the accessors are already
    account-and-good-shaped so no call site moves.

    Add the accessors: stock for an account and good returning an optional count, total
    stock for a good, the produced and consumed totals for a good, the running goods
    residual, and the list of goods that exist. No accessor returns a mutable reference to
    a stock value or a stock vector, for the same reason no accessor returns one for cash.

    Add three operations, each compute-then-commit and each returning the quantity actually
    moved so that a caller subtracts what moved and never what it intended:

    `produce(&mut self, who, good, units)` validates the good and refuses a negative count,
    then commits by adding the units to that account's stock and to the running produced
    total, recording a `Produce` posting that names the account on both legs with the units
    arriving. Units enter the system here; that is what makes the produced total a real
    second source.

    `consume(&mut self, who, good, units)` validates, refuses a negative count, and refuses
    with the insufficient-stock error if the account holds fewer units than asked. It
    commits by subtracting from stock and adding to the running consumed total, recording a
    `Consume` posting that names the account on both legs with the units leaving. Consumption
    must be a real posting and not a bare subtraction: if it only moved the numbers, a
    consumption bug would be invisible in the journal and LEDG-09 could not name it. This is
    also what MKT-06 means by consumption being an explicit modelled step.

    `exchange(&mut self, buyer, seller, good, units, amount)` moves cash from the buyer to
    the seller and units from the seller to the buyer as **one** posting, and returns both
    quantities that actually moved. It is one posting and not two because that is what makes
    zero-sum a per-posting property in plan 02-04 rather than an aggregate one, and because
    two postings can be half-applied where one cannot. The debit account is the buyer — it
    pays cash and receives units; the credit account is the seller. The compute step resolves
    both accounts, refuses a negative amount or a negative count, refuses an overdraft on the
    buyer and refuses insufficient stock on the seller, and computes all four resulting
    values; the commit step performs four assignments and one recorder call, none of which
    can fail. Note in the docs that this phase has no notion of a sale — `exchange` is a
    ledger operation, and what makes it a sale is a Phase 7 decision that changes nothing
    here.

    Extend the private recorder to advance the running goods residual by the posting's net
    effect on the identity: the units the posting adds to the produced total minus the units
    it adds to the consumed total, minus the units arriving less the units leaving. That
    quantity is zero for every well-formed posting of every kind, and non-zero exactly when
    a posting's own legs contradict the totals it claims to move — which is what makes the
    residual localisable. Keep it constant time; never sum the stock vectors here. Increment
    the transaction count for an `Exchange` posting as well as a `Transfer`, and for neither
    `Produce` nor `Consume`: production is not a transaction, and a tick in which firms only
    produced has traded nothing, which is exactly the degenerate state LEDG-08 exists to
    catch.

    Extend `Books::new` to endow every firm slot with the configured initial inventory,
    recorded as an `Endow` posting with the units arriving, **and counted into the running
    produced total**. Without that count the identity fails at tick 0 by exactly the
    endowment, which is the single most likely "it fails on tick 0 and nobody knows why"
    defect in this phase — say so in the constructor's doc comment next to the equivalent
    statement about the opening money stock. Assert at the end of construction that the
    running goods residual is zero, the same way the cash residual is already asserted, and
    extend the construction error to report a goods mismatch with both numbers. The journal
    is still cleared before tick 0 begins, so no endowment posting can satisfy a per-tick
    check.

    Add unit tests in this file for the ledger half: production increases both stock and the
    produced total; consumption beyond stock is refused and leaves stock untouched; a refused
    exchange moves neither cash nor units; a completed exchange moves both and returns both
    actual quantities; an unknown good is refused rather than indexed; and the transaction
    count rises for an exchange but not for a production. Name the module so a
    `books::goods` module-path filter selects it.

    violation a test observes when one corruption trips two checks, and plan 02-04 asserts

    Append `Violation::GoodsConservation { tick, good, produced, consumed, stock,
    delta_units, journal_residual_units, posting }` with the posting optional for the same
    reason money conservation's is: a discrepancy the journal does not describe is a
    reachable case, and the rendered message must say so honestly rather than name a
    placeholder. Its message names the tick, the good, all three quantities and the offending
    posting, so a reader can tell which of the three moved without re-running.

    Write `check_goods` to compare two independently maintained sources for each good that
    exists, exactly as `check_money` does for cash. One side is the identity recomputed from
    the fields — the produced total less the consumed total less the total stock summed over
    every account. The other is the running residual accumulated from the posting legs. Both
    must be zero, and they must agree; report a failure if either condition breaks. Localise
    with the same linear scan for the first posting whose goods residual is non-zero. Do not
    write a binary search here either, and do not factor the two checks into one generic
    helper that hides which residual is being scanned — the money and goods residuals are
    two different quantities and conflating them in a message is how a debugger ends up at
    the wrong column.

    Add a test module proving the identity holds under **both** of the consumption models
    Phase 7 will choose between, because the whole point of this shape is that the choice
    changes nothing here. In the immediate-consumption model, produce at a firm, exchange to
    a household and consume in the same tick, asserting the check passes after every single
    operation and that the household's stock has returned to zero by the end of the tick. In
    the held-stock model, produce and exchange on one tick, end the tick, and consume on a
    later tick, asserting the check passes on both ticks and that the household's stock is
    non-zero across the tick boundary. Assert explicitly that the same check function and
    the same accessors were used in both, so the "one shape" claim is demonstrated rather
    than stated.

    Add one further test asserting that a tick containing only production passes goods
    conservation and *fails* liveness when the gate is on. That is the pair of facts that
    keeps the two checks from being mistaken for each other.

    Name the module so a `invariants::goods` module-path filter selects it, and assert

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-13 | Tampering | units created or destroyed outside a posting | high | mitigate | Every unit movement is a posting, and the running produced and consumed totals are advanced from the operation's arguments while the residual is advanced from the posting's legs, so a disagreement between the two is what the check reports. |
| T-02-14 | Tampering | a half-applied cash-for-units swap | high | mitigate | `exchange` is one posting with a compute step that validates cash and stock before any write, and a commit step containing only assignments. Two postings could be half-applied; one cannot. |
| T-02-15 | Tampering | a vacuous goods check | high | mitigate | The identity is compared against a second, separately maintained source rather than derived from the journal at check time; a single-source check would pass forever. Tests exercise the loop body under both consumption models, so the check is never observed over an empty set. |
| T-02-16 | Tampering | stock index confusion across a firm respawn | medium | mitigate | Stock is keyed on the firm slot, matching cash, and a firm account resolves only when its generation matches the ledger's record, so a stale identity is a typed miss rather than a hit on a different firm's inventory. |
| T-02-17 | Tampering | integer overflow in unit arithmetic | medium | mitigate | Unit counts are signed 64-bit and the release profile enables overflow checks, so a wrap aborts rather than producing a plausible negative inventory; negative counts are refused at the operation boundary. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan. 02-RESEARCH.md § Package Legitimacy Audit records zero new packages, and CI's `--locked` build fails on any lockfile change. |
</threat_model>

<objective>
Turn the tracer's single-purpose RNG stub into the facade every later phase draws through: one
master seed, sub-streams addressed by a bit-packed `(tick, agent, purpose)` nonce, and samplers
that consume a fixed, auditable number of draws.

Purpose: CORE-04 exists so that changing the draw count at one site cannot perturb another
market's trajectory — the property that makes "this economic change caused that outcome" an
attributable claim rather than a hope. `01-RESEARCH.md` demonstrated the property by execution
rather than asserting it, and this plan reproduces that demonstration as a committed test.
CORE-05 sits on top: `rand`'s own range and index samplers were verified to be neither
fixed-draw nor stable across upgrades, so the three samplers this crate uses are hand-rolled.

Output: `src/rng.rs` complete, and `tests/determinism_rng.rs` carrying the isolation
demonstration, the two counter-checks and the exact-draw-count assertions.
</objective>

<assumption_delta_decision>
The advisory assumption-delta detector fired on this phase with a `pluralization` signal (the
phrase "an added draw in one market provably cannot perturb another" in the ROADMAP's Phase 1
success criteria). The identity-model question it raises is real, so it is answered here rather
than left implicit.

- **The noun that is now primary:** the **RNG sub-stream**, addressed by `(tick, agent, purpose)`.
  There is no longer "the simulation's random number generator" as a thing with a position in a
  sequence; there is a keyed address space, and a generator instance is a transient view onto one
  address in it.
- **The decision: `promote`.** The addressed sub-stream is promoted to the primary identity of
  randomness in this codebase, and the single global generator is demoted out of existence rather
  than kept alongside as a fallback. `src/rng.rs` is the only module permitted to construct a
  generator; every other module receives a `Stream` and never a generator, so there is no ambient
  sequence to fall back to. Rationale: keeping a global stream alongside the keyed one would let a
  later phase quietly draw from it, and the isolation guarantee would then hold for some draw
  sites and not others — the asymmetry the promote-vs-add-alongside rule exists to prevent.
- **Invariant test encoding the generalized intent:** already required by this plan as
  `extra_draws_in_one_purpose_cannot_perturb_another` in `tests/determinism_rng.rs` (Task 3). It
  goes red the instant a future phase reintroduces a shared sequential draw source, so the
  regression cannot land silently.
</assumption_delta_decision>

  <decision>Lock the RNG sub-stream key layout before any draw site is written against it</decision>
  <context>
    This is the one genuinely one-way door in Phase 1. The sub-stream key determines every random
    value the simulation will ever produce. Re-keying later does not merely touch call sites: it
    changes the trajectory of every committed run, so every golden log, every `insta` snapshot and
    every calibrated parameter chosen against those runs has to be regenerated and re-reviewed.
    Nine later phases draw through this key.

    CONTEXT.md D-01 and D-02 already record a decision, made by Claude under the delegation the
    user gave in `/gsd-discuss-phase` ("Im unfamiliar with the field you will have to decide"),
    and `01-RESEARCH.md` Open Question 1 nonetheless recommends confirming the bit allocation with
    the user specifically because widening the purpose field later re-keys everything. Confirming
    it now costs one answer; discovering it wrong in Phase 10 costs the run history.

    Measurements behind the recommendation, all taken first-hand on this machine against
    `rustc 1.94.1`: the bit-packed scheme cost 237 ms for 3.65 M sub-streams against 1390 ms for
    SHA-256-derived child seeds (5.9x); `ChaCha8Rng` offers 2^64 streams per seed, each 1 ZiB
    long; the realistic model shape is roughly 3.2 M sub-streams; and the isolation property was
    observed directly — a sub-stream that consumed 7 draws instead of 4 left a sibling sub-stream
    bit-identical.
  </context>
  <options>
    <option id="bitpacked-24-24-16">
      <name>Bit-packed nonce, tick:24 | agent:24 | purpose:16 (recommended — CONTEXT.md D-01, D-02)</name>
      <pros>Bijective, so distinct keys give distinct streams by arithmetic rather than by a collision-resistance argument. 5.9x cheaper than hashing. Headroom for 16.7 M ticks and 16.7 M agents against a realistic need of 3,650 and 220, and 65,536 purposes against a realistic need of about 12 — so adding a purpose or lengthening a run never forces a re-key. Uses the nonce API the cipher was designed around.</pros>
      <cons>The field widths are fixed forever; narrowing or widening any field afterwards re-keys history. Requires an explicit assertion at the packing site so an out-of-range tick or agent fails loudly instead of wrapping into a neighbouring field.</cons>
    </option>
    <option id="bitpacked-narrower">
      <name>Bit-packed nonce with a different allocation (for example tick:32 | agent:20 | purpose:12)</name>
      <pros>More tick headroom if runs are ever expected to exceed 16.7 M ticks.</pros>
      <cons>Buys headroom the model cannot use — a 3,650-tick decade is four orders of magnitude below the 24-bit ceiling — while spending purpose bits, which is the field most likely to grow as later phases add draw sites. Same one-way cost as the recommended option with no measured benefit.</cons>
    </option>
    <option id="hashed-child-seeds">
      <name>SHA-256 over (master seed, tick, agent, purpose), used as a child seed</name>
      <pros>Unbounded key space; no field-width ceiling ever.</pros>
      <cons>Measured 5.9x slower for the model's realistic sub-stream count. Collision-free only probabilistically rather than by construction. Its one advantage — an unbounded key space — addresses a constraint that does not exist, since 64 bits is roughly 100,000x more address space than the model can consume.</cons>
    </option>
  </options>
  <resume-signal>Reply `bitpacked-24-24-16`, `bitpacked-narrower` (and state the allocation), or `hashed-child-seeds`. Replying "approved" selects the recommended option.</resume-signal>

    Complete `Stream` with the three samplers, each consuming a fixed and stated number of draws,
    incrementing the draw counter once per underlying 64-bit draw:

    - `pub fn below(&mut self, n: u64) -> u64` — already present from the tracer; confirm it is the
      multiply-high form over exactly one `next_u64`, with no loop and no second conditional draw.
      Its bias is bounded by `n / 2^64`, which is the trade this project accepts to get a fixed
      draw count.
    - `pub fn coin_ppm(&mut self, p_ppm: u32) -> bool` — exactly one draw, returning
      `self.below(1_000_000) < p_ppm as u64`. Probabilities enter the model as parts-per-million
      integers, never as floats, which keeps every threshold parameter in the integer domain.
    - `pub fn sample_k(&mut self, pool: &mut [u32], k: usize) -> Vec<u32>` — partial Fisher-Yates,
      exactly `k` draws always, asserting `k <= pool.len()`, swapping the chosen element into
      position `i` and pushing it.
    - `pub fn shuffle_in_place(&mut self, pool: &mut [u32])` — full Fisher-Yates over the slice,

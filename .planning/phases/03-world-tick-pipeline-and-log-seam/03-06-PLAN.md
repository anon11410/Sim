<objective>
Close the phase: commit a golden run so a change to the economy is reviewable, and extend the
halt-message guard to the modules this phase added.

Purpose: the determinism suite proves a run reproduces *itself*. It does not notice when a
deliberate rule change moves the whole trajectory — which is exactly what Phases 5 to 11 will do,
one rule at a time. A committed short run turns that into a diff someone reads and accepts.
And guard 7h, which keeps the environment out of a halt message, currently searches only the two
modules Phase 2 wrote; this phase added two more that can carry a violation and one that
legitimately holds a filesystem path, and the guard must be extended to say something true about
each of them.

Output: a committed 50-tick run directory, its regeneration command, its reproduction test, and
an extended guard.
</objective>

    **How the run is produced.** Build the 50-tick configuration by textual substitution over the
    shipped file, exactly as the criterion-6 test builds its override: read the shipped

    result into a temporary directory. Assert the count before substituting, for the same reason

    comparison would fail with a confusing message about file length rather than a clear one about
    the substitution.

    Do **not** commit a second configuration file. Deriving the golden configuration from the
    shipped one means every parameter except the tick count is the shipped parameter, so a
    deliberate parameter change shows up as a golden diff — which is the entire point. A committed
    copy would drift and would then be certifying a configuration nobody runs.

    **What is committed.** The three diffed files only: the tick series, the event stream and the
    provenance table. **Not** the run record: it is excluded from every diff by the locked
    decision, it carries the compiler version string, and committing it would make a toolchain
    bump look like an economic change.

    Use seed 42, the shipped seed, so the golden run and the shipped configuration tell one story.

    **The window is 50 ticks, and the reason recorded in the project research is wrong.** That
    document says all 3,650 ticks would make a deliberate rule change unreviewable. Measured, a
    *localised* change diffs to the same four-line hunk at either length, because a diff prints
    only the hunk. The real numbers are for a **trajectory-wide** change: 102 diff lines at 50
    ticks against 7,302 at 3,650, and 203 kilobytes rewritten in the repository on every
    deliberate change instead of under three. Record the honest reason in the golden directory's
    own note.

    **And one constraint the research adds: the window must span at least two planning cycles**,
    or a cadence-length effect is invisible in it. The cadence is a 21-day month, so the floor is
    42. Fifty satisfies it with margin, which is the strongest argument for the number. Write that
    down beside it, so a later reader does not shrink it to twenty.

    **The regeneration script.** Add `tests/regenerate_golden.sh`: it performs the substitution,
    runs the built binary, and copies the three files into the golden directory — and nothing
    else. Regeneration is a deliberate operator act with a reviewable diff, in the same mould as
    the schema and the lint configuration. The test **never writes**.

    mismatch it must report the **first differing line number and both lines** — reuse the helper
    plan 03-04 added for the schema — and must name the regeneration script in its message, so a
    reader whose change was deliberate knows exactly what to run and a reader whose change was not
    sees which tick moved.

    of the phase validation map.** The build runs the whole suite in both the debug and the
    release profile. This test compares the current profile's output against **one** committed
    artifact, so if a profile-gated byte ever reached a log, one of the two passes would go red.
    That is the debug-and-release agreement claim, delivered without spawning a build from inside
    a test — which would deadlock on the build lock. Say so in the test's own doc comment.

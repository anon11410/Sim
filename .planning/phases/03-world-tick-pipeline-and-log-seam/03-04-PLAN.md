<objective>
Freeze the wire format: generate the log schema from the writers, commit it, and prove the drift
test fires.

Purpose: `schema/schema.json` is the contract between this binary and Phase 4's Python harness
across the disk boundary, and whatever it freezes here is what Phases 5-11 append to. The
obvious way to build it — a second derive macro over the same types — was compiled against a
replica of this repository's own posting type and **measured wrong**: the JSON writer emits an
address as a short string while the schema generator declared it an object, because a derive
cannot see a custom serialiser, and this project uses one on both address fields. A generator
and a committed file that are wrong in the same way agree with each other forever, so the drift
test would never fire. The schema is therefore read out of the bytes the writers actually
produce.

Output: a committed schema, a mode flag that regenerates it, three shape tests and one mutation
proof wired into the build.
</objective>

    <!-- planner-discipline-allow: schemars, float64, int64, dtype -->
    Add the schema generator to the log module. It is roughly ninety lines and adds no
    dependency.

    Four pieces:

    1. A classifier mapping a parsed JSON value to a short type name: a string to a string, a
       boolean to a boolean, an integral number to a 64-bit integer, any other number to a
       floating type, a null to a null, and anything else to an explicit unsupported marker
       rather than to a guess. The unsupported marker matters — a silent fallback would let a
       shape the Python side cannot read pass as though it were understood.
    2. A reader returning the ordered field-name-and-type pairs of any serialisable value:
       **take the key order from the emitted text** — which is declaration order — and the type
       from parsing that same text. This is the whole trick. A field rendered by a custom
       serialiser is reported as whatever it actually became, so an address that renders to a
       short string is typed as a string. There is no second description of the types anywhere,
       so the schema cannot disagree with the file.
    3. A reader returning the ordered column-name-and-type pairs of a CSV row type: the names
       come from **the header the CSV writer itself emits** for an exemplar row, and the types
       from the same serde implementation. Column order is the contract for the tick file; a
       generator that sorted its output alphabetically would not record it.
    4. The public generator, returning a deterministic string: the schema version, then the tick
       file's columns, then the provenance file's columns, then one entry per event variant with
       its ordered fields. Compose the text yourself in a fixed order rather than through a map
       type, so the ordering is a property of the code and not of a container.

    **This is deliberately not the obvious approach, and the SUMMARY must record why.** A schema
    derive macro is the obvious choice and this project's earlier research named one. It was
    compiled here against a replica of this repository's posting type: the JSON writer produced
    a short address string while the derive declared the same field a tagged object, because the
    derive is a second, independent macro that cannot see a custom serialiser — and this project
    uses one on **both** address fields. It also emits properties alphabetically, so it does not
    record CSV column order at all. A generated file and a generator that are wrong in the same
    way agree forever and the drift test never fires. That is the failure this design closes, and
    it is why no schema-derive crate is in the manifest.

    Add the difference helper alongside: given a generated text and a committed text, return the
    first line number at which they differ together with both lines. The raw equality assertion
    prints a multi-kilobyte single-line escaped blob, which no one reads; a line number and two
    lines is a reviewable diagnostic. No dependency is needed.

    Nothing in this module may name a floating-point type. The type name the classifier returns
    for a non-integral number is a **string literal of a pandas dtype name**, which the
    confinement guard does not match — the guard requires identifier boundaries around a float
    type name and there is none inside that word. That was measured; do not restructure it into
    something that does name the type.

    Add unit tests in the module for the behaviours listed above, reachable by a filter on the
    module's name.
